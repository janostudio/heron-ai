heron-ai 服务化部署与 Web 页面

把 heron-ai 从「前台 CLI 工具」变成「可部署的服务」，页面是它的基本入口。 本稿侧重界面与交互的细节规格；技术决策与取舍见 DESIGN-web-ui.zh-CN.md。

0这份稿子改了什么

上一版把页面写成「定时唤醒的配套」，需求起点是"看不到唤醒产出"。那是把基础设施降级成功能补丁。 这一版换起点：heron-ai 现在只能当前台 CLI 用，缺的是能部署成一个服务。

旧起点

看不到 agent 做了什么

于是页面被当成 wakeup 的展示层。做完之后，服务化的问题一个没解决：谁持执行权、多前端怎么共享、怎么访问。

新起点

只有前台进程形态

关掉终端就没了；没有别人能连的入口；CLI 与 HTTP 各自 build 一个 runtime，会写坏同一个 session。

结论

服务化的三个要件

常驻与优雅退出（已有）、唯一的执行权（缺）、可访问的入口（缺）。页面是第三件的一半，另一半是 API。

1定位：不是页面，是服务

服务化之后，用户面对的不再是"一个命令"，而是"一个地址 + 一组前端"。三个前端共享一个执行宿主。

1.1 执行宿主与前端

heron-ai serve · 唯一执行宿主
Runtime → WakeupScheduler → SessionWriter
唯一持有 runtime 与 session 写权
HTTP + SSE /api/*
静态页面 go:embed
TUI 客户端
本机进程内，或 attach 远端
浏览器
本地 / 局域网 / 反代
机器消费者
curl / SDK / IM 网关

1.2 四种启动方式，一个内核

命令执行宿主前端用途
heron-ai本进程进程内 TUI + 浏览器本机日常：终端干活，顺手开页面
heron-ai --serve本进程无（纯 HTTP/SSE）部署：systemd / 容器常驻
heron-ai attach <url>远端 serve进程内 TUI连远端，本地不起 runtime
heron-ai -prompt本进程无脚本 / CI，跑完退出
无参数不等于另一种模式 它建一次 bundle，然后用同一份 bundle 起 HTTP 并跑 TUI。所以进程内 TUI 就是 serve 的一个前端，Ctrl-C 时一起退、不留后台残留。

2唯一约束：执行权必须收敛

runTUIWithSession（cmd/server/main.go:905）在自己的进程里 buildCurrentRuntime，而 JSONLSessionWriter.nextSeq 是进程内存的。 两个进程写同一个 flow.jsonl，各自从 1 开始分配 seq，事件流直接乱掉。 

heron-ai --serve   → 进程 A，持有 runtime，写 .agents/data/sessions/<id>/flow.jsonl
heron-ai           → 进程 B（TUI），又 build 了一个 runtime，也写同一个文件
                     ✗ seq 冲撞
                     ✗ 页面与终端看到两份状态

所以页面不能是"再起一个进程"，CLI 也必须进到那个执行宿主里。落点是把当前互斥的两个分支拆开：

buildCurrentRuntime → bundle
├─ serveRuntime(bundle, host, port, token) 只起 HTTP
├─ runTUIOnBundle(bundle) 只跑 TUI
└─ 无参数时两者都调用，共享同一个 bundle

4设计令牌

颜色、字号、间距只从这套令牌取，组件里不写裸值。亮/暗两套通过 data-theme 切换，跟随系统偏好。

4.1 语义色

令牌亮色用途不要用在哪
--c-accent#2456E6主按钮、链接、选中态、运行中指示状态告警（那是 warn/danger）
--c-ok#067647工具成功、ready、通过正文文字
--c-warn#B54708定时检查、待审批、需要人看一眼错误（错误用 danger）
--c-warn-line#F79009wakeup 回合的左侧竖条、待审批边框大面积填充
--c-danger#B42318失败、取消、拒绝普通提示
--c-text-muted#667085次要信息、元数据正文主色

4.2 排版

层级字号 / 行高用在哪
页面标题24 / 1.35，字重 600，字距 -0.02em会话标题
区块标题16 / 1.35，字重 600面板标题
正文14 / 1.6消息正文、表单
次要13 / 1.6元数据、说明
小字12 / 1.6标签、时间、表格
微字11 / 1.6徽标、路径、工具参数
等宽ui-monospace，0.92em 相对工具名、会话 id、时间戳

为什么时间戳用等宽：时间列在列表里上下对齐，比例字体的冒号宽度不一致会让整列看起来在抖。

4.3 间距与形状

4px 网格

所有内外边距取 4 的倍数：4 / 8 / 12 / 16 / 20 / 24 / 32 / 40 / 48。组件之间最小间距 8，块之间 16，区块之间 32。

圆角

小控件 4（按钮、输入框内元素）、卡片与工具块 8、浏览器外壳 12、标签与徽标全圆。

4.4 密度

位置高度说明
会话行最小 56，随内容增长两行结构：标题 + 元数据
工具调用行（折叠）32超过 10 个时默认全折叠
输入框64（2 行）→ 最大 200超出滚动，不自动撑满视口
审批条40紧贴输入框上方，不浮层

5组件规格

六个核心组件。每个都给出结构、字段来源与状态样式，实现时按这里的字段映射，不要另造结构。

5.1 会话行 .session-row

栅格
18px | 1fr | auto，列间距 12
第一列
状态点：idle 灰 / running 蓝（带 3px 光晕）/ waiting 琥珀 / failed 红
标题行
sessionlist.Session.Title，右侧可跟 未读 N 徽标
元数据行
{Turns} 轮 · {Tokens} tok · 最后活动 {相对时间}，有定时器时追加琥珀色「N 分钟后有一次定时检查」
右列
会话 id（等宽，11px，faint）+ 状态文案
点击
整行进详情；右键/长按不做任何事（V1 不提供上下文菜单）

相对时间规则：小于 1 分钟「刚刚」；小于 1 小时「N 分钟前」；今天内「HH:MM」；昨天「昨天 HH:MM」；更早「MM-DD」。这条规则同样用于详情里的消息时间。

5.2 消息块 .msg

栅格
56px | 1fr：左列角色名右对齐，右列内容
角色来源
用户显示「你」；Team 产生的消息显示 team_id；协调者显示「助手」
变体 · 普通
无装饰，正文 14/1.6
变体 · intermediate
整体 opacity:.72 + 左侧 2px 虚线；含义是「这一步不是答案」，不参与未读计数
变体 · wakeup
左侧 2px 琥珀实线 + 「定时检查」徽标 + 「你不在时」标签；参与未读
正文渲染
textContent + 白名单 markdown（代码块、粗体、列表、链接）。禁止 innerHTML

5.3 工具调用 .tool

折叠行
▸ 工具名 · 参数摘要 · …… · 状态 · 耗时
参数摘要
取工具入参里最有辨识度的一个字段：Bash 取 command，Read/Edit/Write 取路径，Grep 取 pattern，单个值超过 46ch 截断加省略号
状态文案
成功 · 失败 · 进行中（进行中时行尾显示脉动点，不显示耗时）
展开体
等宽 11px，最大高 240 滚动；超过 3 行时默认折叠，头部显示「展开 N 行」
来源事件
tool_call.started / completed / failed，见第 7 节

5.4 交付物 .deliveries

位置
挂在产生它的回合正文下方，不单独成页
头部
「N 条交付物」，可折叠，默认展开
单条
第一行 team_id（等宽 11px faint），第二行正文
来源
payload.deliveries[]：{text, team_id, message_id}
为什么要单独成块
交付物是用户必须看到的独立结果，不是协调者的评论。混进 reply 会让「谁说的」丢失

5.5 审批条 .approval

位置
输入框上方，占一整行；有 pending_approvals 才出现，多个时纵向堆叠
内容
工具名 + 完整命令/路径 + 「允许 / 拒绝」
拒绝
点开后出现原因输入（可选），提交后条消失
来源
payload.pending_approvals[]，或 /api/status 的返回
不做的
不做 toast、不做角标弹窗——审批是阻塞动作，必须留在视线里

5.6 断线横幅 .banner

文案
「连接断开，N 秒后重连…（已有内容保留，不会清空）」
位置
顶栏下方，通栏；恢复后自动消失
关键行为
不清空已有内容。重连成功后用 Last-Event-ID 续传，补齐断线期间的事件

6状态矩阵

每个页面在四种非正常状态下长什么样。这些状态不写进设计就会在实现时各写各的。

7事件 → 界面映射

这一节只讲对话视图的投影：哪些事件会变成一条消息、按什么规则合并。 引擎产生的 53 类事件里，大部分不进入对话（Team 批次、Call、邮箱、记录、压缩、恢复），它们属于追踪视图，见第 14 节。

帧形状（真机验证过的坑） data: 里是扁平事件头 + 嵌套 payload。seq / type / flow_turn_id / created_at 在顶层； origin / reply / intermediate / deliveries / contributors 在 payload 内。 把 flow_turn_id 当 payload 字段读会拿到空串，去重与日志同时失效。
事件 type驱动什么关键字段
flow_turn.started 时间线开新块；会话行状态点转蓝 顶层 flow_turn_id；payload.input（用户回合时显示为「你」的气泡）
agent.model_response 追加助手正文（流式则逐字追加，否则整段） payload.text、payload.round
tool_call.started 插入折叠工具行，状态「进行中」 tool_name、arguments、tool_call_id
tool_call.completed / failed 更新同一 tool_call_id 的行：状态与耗时；失败时展开体自动打开 content / error
flow_turn.waiting_input 回合收尾：按 origin 决定样式（user 普通 / wakeup 琥珀 / 其它 intermediate 灰）；非当前会话时累加未读 payload.origin、reply、intermediate、deliveries
wakeup.created 列表页追加「N 分钟后有一次定时检查」；定时页插入一行 scheduled payload.wakeup.{id, fire_at, note, team_id}
wakeup.fired 定时页该行转 fired；详情页标题栏倒计时改为「正在检查」 同上
wakeup.skipped 定时页该行显示 skipped + 具体原因；倒计时更新为新的 fire_at payload.reason（如「用户 70 秒前说过话，落在 5 分钟静默窗口内」）
wakeup.expired / cancelled 定时页该行置灰，不再倒计时 —

7.1 合并与去重规则

  • 按 seq 严格递增渲染：收到小于等于已渲染最大 seq 的帧直接丢弃（重连 replay 会重发）。
  • 工具行按 tool_call_id 复用：started 建行，后续 completed/failed 只更新不新增。
  • 回合按 flow_turn_id 归组：同一回合的 model_response 与工具行都挂在该回合块下。
  • 未读：当前不在该会话页面时，flow_turn.waiting_input 且 intermediate=false 才 +1；进入会话即清零。intermediate 不计。
  • 去重键：event_id（每帧自带），用于兜底防重复渲染。

8关键交互时序

四条最容易做错的路径。每条都标出「用户看到什么」与「发什么请求」，实现时按这个顺序写。

8.1 打开会话（历史 + 增量）

  1. 拉历史：GET /api/sessions/{id}/history
    渲染已有消息，并记住 max_seq = 33——它是下一步的断点。
  2. 接增量：GET /api/stream?session_id={id}&follow=1
    请求头带 Last-Event-ID: 33，只要 33 之后的事件。
  3. 收到 seq 34… 起逐条追加
    之后不再重拉历史，也不重新渲染整页。
为什么不是"先连流再拉历史"先连流会在历史到达时重排一次，页面闪一下。先历史后增量，页面只追加。

8.2 发消息

  1. 本地立刻插入一条「你」的气泡，标 pending
    浅灰、不可编辑。交互不等网络。
  2. 提交：POST /api/sessions/turn?session_id={id}
    请求体 {"input": "…"}。
    2xx → 气泡转正（去掉 pending 标记）
    4xx → 气泡标红 + 错误文案 + 「重试」按钮，保留原文不清空
    超时 / 断网 → 气泡标「待发送」，重连后自动重发一次，仍失败转手动
  3. 后续内容全部来自 SSE，不用 POST 响应体渲染
    POST 响应里也有 Reply / FinalReply，用它渲染正文会与 SSE 重复一次。POST 只用来判断"受理成功/失败"。

注意：POST 响应里也有 Reply/FinalReply，但页面不用它渲染正文——否则 SSE 再来一次就是重复。POST 只用来判断"受理成功/失败"。

8.3 审批

  1. SSE 推来 agent.pending_approval
    审批条出现；输入框置灰；页面标题加「待审批」标记。
  2. 点「允许」→ POST /api/approvals
    {"request_id":"…","approved":true,"reason":""}；按钮进入 disabled，文案「提交中…」。
  3. 点「拒绝」→ 展开原因输入（可选）→ 同一接口，approved:false
    原因会进 reason 字段，模型能看到拒绝理由并换做法。
  4. 审批条只在拿到明确结果后消失
    成功则收起；失败则保留并提示错误，可重试。不做超时自动收起、不做 toast——审批是阻塞语义。

审批条不做自动消失。它消失的唯一条件是拿到明确结果，因为审批是阻塞语义。

8.4 断线重连

  1. SSE 断开
    横幅出现「连接断开，3 秒后重连…」；已有消息保留，不清屏。
  2. 退避重连：1s → 2s → 4s → 8s → 16s → 30s（上限）
    每次带 ±20% 抖动，避免多个标签页同时重连打满引擎。
  3. 重连带 Last-Event-ID = 本地最大 seq
    引擎从该 seq 之后 replay，不是全量重放。
  4. 连上 → 横幅消失，补渲染断线期间的事件
    补渲染同样按 seq 递增，丢弃重复。
  5. 连续 6 次失败（约 1 分钟）→ 停止自动重连
    横幅改为「无法连接引擎」+「重试」按钮 +「查看 /api/health」链接。

8.5 取消回合

  1. 点「取消回合」→ 内联二次确认
    按钮文案变为「确认取消？」，3 秒内不点则复原。不用弹窗。
  2. 确认后 POST /api/cancel?session_id={id}
    成功后该回合标「已取消」，未完成的工具行标「中止」。
  3. 若返回 409（回合已结束）
    提示「该回合已结束」，同时刷新会话状态，避免界面停在旧状态。

11安全

这个页面背后是一个能跑 Bash、能写文件的 agent。它的 XSS 不是"弹个窗"，是执行权转移。

11.1 三条硬规则

禁止 innerHTML

一律 textContent 或转义后插入。markdown 只渲染白名单子集（代码块、粗体、列表、链接）。链接强制 rel="noopener noreferrer" 且只允许 http/https。

CSP

default-src 'self'; script-src 'self'; connect-src 'self'; img-src 'self' data:。页面里不写内联 <script>、不写 onclick 属性。

token 不进 URL

不放 query（会进历史、Referer、代理日志）。对外模式走 POST /api/login 换 HttpOnly; SameSite=Strict cookie。

11.2 攻击面清单

面风险措施
模型输出HTML/JS 注入纯文本渲染 + 白名单 markdown + CSP
工具输出同上，且可能是 ANSI 转义序列剥离 ANSI 后按纯文本渲染
静态路由路径穿越读文件只从 go:embed 的 FS 读；未命中一律 404，不退化成 http.Dir
写操作CSRF（第三方页面代发）cookie 模式要求 X-Requested-With；SameSite=Strict
非 loopback 暴露无认证访问能执行命令的界面强制 token + 登录；启动时打印醒目警告

13边界与异常

这些情况不写清楚，实现时会各写各的，最后变成线上事故。

情形行为
会话在另一个进程里正跑着不该发生（执行权唯一）。若 serve.lock 检测到第二实例，直接启动失败并提示用 attach
会话文件被外部清理/history 返回空 → 页面显示「会话数据不存在」+ 返回列表；不自动重建
事件流出现未知 type忽略，不报错，不渲染占位（前向兼容：新版本引擎加事件时旧页面不崩）
同一回合事件乱序到达按 seq 排序后再渲染；本地维护「已渲染最大 seq」，小于等于它的丢弃
消息正文超长（> 50KB）折叠为「展开全文」，避免一次插入几万字符卡住渲染
单会话事件超过 2000 条只保留最近 1000 个 DOM 节点，更早的折叠为「更早的 N 条消息」
定时器在一个已删除的会话上触发引擎侧已处理（wakeup.expired）；页面把该行标灰
浏览器不支持 SSE退化为 3 秒轮询 /api/sessions/{id}/history?after_seq=N，并在页脚提示「实时更新已降级」
多标签页打开同一会话各自独立连接；写操作不互斥（后发者覆盖不了前者，因为服务端是队列语义）；未读状态按标签页各自维护
用户在没有 serve 的情况下直接 heron-ai进程内同时起 HTTP 与 TUI，页面可访问；Ctrl-C 一起退出，端口释放
多人访问（多用户）V1 明确不支持：没有会话归属、没有只读角色、没有审计。要么部署在内网单用户机器，要么等独立的多租户设计
一个必须承认的缺口 现在整份设计是单用户模型：谁能访问页面，谁就能操作这个能跑 Bash 的 agent。 如果目标是把页面开给一个团队用，还需要一层「会话 → 用户映射 + 只读/可写权限 + 审计日志」， 那不是 P4 的部署物料，而是一个独立设计。

14会话记录：一份数据，三种呈现

上一版把会话拆成三个视图、三个接口（history / trace / events），要拼起来才看得懂一次执行。 这是错的。引擎那边本来就是一份只增不改的记录——三层事件文件、session 级 seq、 完整的 scope 链；界面不该把它切开。

14.1 为什么必须是一份

对照

DeepSeek Harness 的做法

一份 append-only 的会话日志记录模型看到的一切（系统提示、每轮思考、工具参数与结果、子 agent 调度、每次上下文注入），轨迹视图在一个页面里回溯。第三方插件把它渲染成横向时间轴 + minimap + 逐站回放。

heron 的现状

数据已经是一份

sessionID 一个目录、三层 jsonl、seq 全局递增、EventHeader 带完整 scope 链。eval.SessionFacts 的注释就写着「the merged three-layer timeline」。

结论

切分是在界面层自找麻烦

三个接口意味着三次加载、三套分页、三份缓存，还得自己对齐时间。用户想知道「第 8 条事件前后发生了什么」，却要在三个页面之间跳。

14.6 原始请求：模型到底看到了什么

这是回溯里最容易被忽略、但排查 prompt 问题时最有用的一块。heron 已经有数据： AgentTranscript 存在 .agents/data/agent-transcripts/<id>.json， 按 flow_session_id + team_id + call_id + agent_id 分文件，含累积的 Messages 与 SystemHash（系统提示变更检测）。

记录页里，每个 agent.model_response 站点可以展开「原始请求」面板，显示：

  • 该轮之前重建的消息列表（从 transcript 截取到该轮）；
  • 系统提示与工具目录（按 SystemHash 取对应版本的摘要）；
  • 本次请求与上次的差异：新增/移除了哪些工具、注入了哪些 context 块；
  • token 明细（输入 / 输出 / 缓存命中）。
一个已知的精度限制 transcript 是「累积的消息列表」，不是「每次请求的完整快照」。要精确还原某一轮发了什么，需要按该轮的 agent_turn_id 截取前缀并重建系统提示。如果后续要做像素级复现，应在 agent.model_response 里补一条 request_digest（message 数、system hash、工具名列表、token），成本很低但能让重建免于猜测。

15.3 纵向顺序不是时间顺序

这是画树时最容易错的一条。行序表达的是归属与开始先后，不是结束先后。 引擎里各层的并发语义并不一样：

层能否并行依据
回合 flow_turn 同会话串行，但可以交错 六个推进入口都持 resumeLock(sessionID)，所以不会真的同时跑；但前一个回合进入 waiting_tool 挂起后，后一个（resume / wakeup）可以起来——于是「回合 1 先开始、回合 2 先结束」是正常现象
TeamTurn 并行，上限 20 limitActivations(ready, MaxParallelTeams)，MaxParallelTeams 默认 20
Call 并行，上限 MaxParallelCalls limitCalls(ready, MaxParallelCalls)（internal/runtime/team/runtime.go:194）
round 内工具 并行，上限 MaxParallelTools 注释明确：「Tool parallelism is inside one AgentTurn and is not a Flow/Team orchestration level」

由此定的三条规则

  1. 排序按 first_seq 升序：谁先开始谁在上。不按结束排——按结束排会让子节点跑到父节点上面，归属结构就散了。
  2. 重叠即并行：兄弟节点的区间条有交叠，说明它们同时在跑。不额外加「并行」标签，条本身就是证据（标签会随事件增长而过期）。
  3. 结束先后只看条右端：耗时列给绝对数字，区间条给相对位置。两者一致，行序不参与判断。
还有一个会让区间条变长的因素 waiting_tool / waiting_approval 也算「离开 running」——eval.Graph 把任何终态事件都当作 FinishedAt。 但回合可以被 resume 继续，继续后 last_seq 会被推后。所以一个回合的区间条可能在恢复后变长，这不是 bug，是「它确实活了这么久」。 界面上用实线段 + 虚线段区分「连续执行」与「挂起等待后恢复」。
