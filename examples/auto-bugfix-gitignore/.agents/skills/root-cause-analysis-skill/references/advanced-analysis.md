# 四阶段根因分析详细步骤

> 从 `SKILL.md` 按需加载。包含每阶段的详细执行方法、反证三连、对比法等。

---

## 阶段 1: 现象定位

明确 Bug 的**外在表现**，不急于看代码：

- **复现路径**：用户执行了什么操作触发了 Bug？（从 Issue 描述/沙箱日志提取）
- **预期行为**：正常情况下应该发生什么？
- **实际行为**：实际发生了什么？
- **影响范围**：哪些用户操作/场景会触发？是否100%复现？
- **页面上下文**：Bug 发生在哪个页面？该页面由哪些组件组成？参考 `knowledge/page-components.md`

输出格式：

```
【现象定位】
- 复现路径: {用户操作步骤}
- 预期: {应该发生什么}
- 实际: {实际发生了什么}
- 范围: {影响面评估}
```

### AC 产出（bug_behavior）

阶段1结束时，根据"预期 vs 实际"差异，产出 `acceptance_criteria` 中的 `bug_behavior`：

```
AC-B1 [bug_behavior]:
  Given {前置条件——谁、在什么状态}
  When {触发动作}
  Then {当前错误结果——必须是可观测的，如状态码500、报错文本、UI异常表现}
```

> **注意**：Then 必须精确可观测（状态码、报错信息、页面表现），禁止"报错"/"不正常"等模糊描述。

## 阶段 2: 假设生成

基于现象，生成**至少 2 个**可能的根因假设。每个假设必须包含验证方法。

尽量避免只生成 1 个假设——单一假设容易导致确认偏误（只找支持自己假设的证据）。

```
【假设 A】{一句话描述}
- 可疑位置: {文件:行号 或 函数名}
- 验证方法: {怎么确认或排除这个假设}

【假设 B】{一句话描述}
- 可疑位置: {文件:行号 或 函数名}
- 验证方法: {怎么确认或排除这个假设}
```

假设生成的思考方向：
- **数据流**：数据从哪来？经过哪些处理？哪一步可能出错？
- **状态管理**：哪些状态变量参与？是否有竞态/未同步/未重置？
- **边界条件**：空值、undefined、数组越界、异步时序？
- **最近变更**：`knowledge/hotspots.md` 中最近改过的相关文件？
- **状态持久化**：涉及的状态存在哪里（内存/localStorage/sessionStorage）？页面刷新/跳转后是否保留？参考 `knowledge/state-lifecycle.md`
- **技术约束**：是否有存储限制、数据体积问题、已知反模式？参考 `knowledge/tech-constraints.md`
- **系统配置**：相关配置项是否最近变更（`git log -- <config-file>`）？环境变量是否正确（`pm2 env` / `ecosystem.config.js`）？
  注意：沙箱中的 CLI 启动参数是 prewarm 时冻结的，`set_config` 只能改白名单内的配置。
  检查点：`permissions.deny`、`disallowedTools`、API endpoint、模型超时、skill tool char budget 等白名单外配置——是否在最近 commit 中变更但未在沙箱中反映？

---

## 阶段 3: 假设验证

对每个假设逐一验证。验证应基于**代码事实**，而非推测。

验证手段（优先级从高到低，有日志时必须先看日志）：
- **查看沙箱日志（P0，有 ACP URL 时必做）**：日志中的错误信息比 Issue 描述更精确
- 读取源代码，追踪数据流和控制流（日志引导下精确定位）
- 搜索关键函数的调用链（grep / codebase_search）
- 查看 git log 确认最近的相关变更
- 对比正常流程和异常流程的代码路径差异

```
【假设 A 验证】
- 过程: {做了什么验证}
- 结果: ✅ 确认 / ❌ 排除 / ⚠️ 无法确定
- 证据: {具体代码行 / 日志片段}

【假设 B 验证】
- 过程: {做了什么验证}
- 结果: ✅ 确认 / ❌ 排除 / ⚠️ 无法确定
- 证据: {具体代码行 / 日志片段}
```

如果所有假设都被排除，尝试生成新假设。如果信息不足无法深入，选择最可能的方向推进，在 PR 描述中标注置信度。

## 阶段 4: 根因确认

确定根因，给出修复方向：

```
【根因确认】
- 根因: {一句话描述真正的原因}
- 置信度: 高/中/低
- 证据: {代码文件:行号 + 关键代码片段}
- 为什么会出现: {这段代码为什么有问题，是遗漏/逻辑错误/竞态/...}
- 修复方向: {最小改动方案，改哪个文件的哪个函数}
- 影响评估: {这个修改是否可能影响其他功能}
- 配置排除: {是否已检查相关配置变更？有/无异常}
```

### AC 产出（expected_behavior + regression_safety）

根因确认后，产出完整的验收标准：

**expected_behavior**（修复后正确行为）：
```
AC-E1 [expected_behavior]:
  Given {修复后的前置条件}
  When {修复后的触发动作}
  Then {修复后应达到的正确结果——可观测的状态码/返回值/UI文本}
```
- 来源：根因分析过程中明确的"应该发生什么"
- **Then 必须可观测**（状态码 200、弹窗文本"上传成功"、日志出现某字段），禁止"正常"/"没问题"

**regression_safety**（回归防护——修复不能破坏的现有功能）：
```
AC-R1 [regression_safety]:
  Given {不受影响的前置条件}
  When {不受影响的操作}
  Then {SHALL CONTINUE TO: 现有正确行为必须保持}
```
- 来源：对 `affected_files` 做 `grep -rn "{函数名}"` 找到的调用方
- **每个 affected_file 至少推导 1 条回归防护**

## 危险信号自检

在阶段 4 输出后，快速自检：

| 危险信号 | 处理 |
|---------|------|
| 根因 = Issue 描述的原话 | Issue 描述是**现象**，不是根因，尝试再深入一层 |
| 只生成了 1 个假设 | 补充至少 1 个替代假设再验证 |
| 假设验证只读了 1 个文件 | 追踪调用链，至少看上下游各 1 层 |
| 修复方向涉及 ≥4 个文件 | 审视是否找对了根因，真正的根因通常改动更集中 |
| 修复方向是"加一个 if 判断绕过" | 检查是否有更本质的修复方式 |
| 根因在后端但只看了前端 | 跨到 repos/genie 验证后端逻辑 |
| 修复方向涉及读取环境变量/配置文件 | 检查配置文件是否在最近被修改，确保变量名和值正确 |
| Bug 是有沙箱才出现或只在特定版本出现 | 检查沙箱 prewarm 配置与当前代码是否一致——prewarm 时 CLI 参数已冻结，白名单外配置无法热更新 |

## 简化条件

| 情况 | 简化方式 |
|------|---------|
| 纯样式问题（CSS/布局） | 阶段 2 可只生成 1 个假设 |
| 拼写错误/常量错误 | 四阶段各用 1 句话即可 |
| knowledge/patterns.md 中有完全匹配的已知模式 | 引用已知模式，阶段 2-3 可跳过 |
| 纯配置问题（缺少/错误的环境变量/配置项） | 阶段2可只生成1个假设，直接确认后 fix_direction 写清改哪个配置文件 |
| Issue 信息极度不足 | 完成阶段 1，标注信息缺失，直接进入代码搜索 |
